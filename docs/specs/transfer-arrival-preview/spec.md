# 환승 도착 정보 미리보기

## User-visible outcome

사용자가 출발지·목적지 지명을 입력하면 각각에 가장 가까운 정류장/역이 추천되고, 그 두 지점을 잇는 환승 1회 경로를 안내받아, 환승 지점(버스 정류장 또는 서울교통공사 운영 지하철역)에서 탈 다음 버스/지하철의 도착 예정 시간을 확인할 수 있다.

## Scope

- 출발지·목적지 지명 입력 → 각 지명에 가장 가까운 정류장/역 추천 → 그 두 지점을 잇는, 환승 지점 1곳을 포함한 경로(첫 구간, 환승 지점, 다음 구간) 안내
- 지명과 가까운 정류장/역의 매칭, 그리고 경로·도착 정보는 모두 미리 정해둔 소수의 예시 데이터 조합으로 제공한다. 실제 지오코딩이나 경로 탐색을 수행하지 않는다
- 환승 지점에서 사용자가 확인하면, 그 지점에서 탈 다음 교통편(버스 또는 지하철)의 도착 예정 시간을 볼 수 있다
- 이동 수단은 버스와 지하철을 다룬다. 지하철은 서울교통공사가 운영하는 노선(1~9호선 등 서울교통공사 관할 구간)만 다루며, 신분당선·공항철도·수인분당선 등 다른 사업자가 운영하는 구간은 다루지 않는다
- 도착 정보는 실제 버스 도착정보 API(TAGO/서울시 버스도착정보)와 서울시 지하철 실시간 도착정보 API의 응답 스키마를 그대로 본뜬 예시 데이터로 제공한다. 새로 조회할 때마다 예시 데이터 내에서 값이 달라져, 정적으로 고정된 화면이 아니라 매 조회마다 갱신되는 동작을 확인할 수 있다
- 환승은 1회(구간 2개)로 제한한다
- 위치를 자동으로 추적하지 않는다. 사용자가 직접 확인 동작을 해야 도착 정보가 갱신된다 (PRODUCT.md 확정 사항)
- 경로나 이전 조회를 저장하는 계정·즐겨찾기 기능은 두지 않는다 (PRODUCT.md 확정 사항)

## Acceptance criteria

- 미리 정해둔 예시 지명 중 하나를 출발지에, 다른 하나를 목적지에 입력하면, 각각에 가장 가까운 정류장/역이 추천된다.
  - 예시 1: 출발지 "판교역"을 입력하면 "판교역.버스환승센터" 정류장이, 목적지 "잠실역"을 입력하면 "잠실역"이 추천된다.
  - 예시 2: 출발지 "여의도"를 입력하면 "여의도역" 정류장이, 목적지 "합정"을 입력하면 "합정역"이 추천된다.
- 추천된 두 지점을 잇는, 환승 지점 1곳을 포함한 경로(첫 구간 → 환승 지점 → 다음 구간)가 화면에 표시된다. 구간은 버스 또는 서울교통공사 운영 지하철 구간일 수 있다 (예시 1의 경우 "판교역.버스환승센터"에서 버스 탑승 → "강남역"에서 하차해 지하철로 환승 → 2호선으로 잠실 방향 이동, 과 같은 흐름).
- 환승 지점에서 다음에 탈 교통편(버스 또는 지하철)의 도착 예정 시간이 화면에 표시된다.
- 같은 환승 지점을 다시 조회하면 도착 예정 시간 값이 이전 조회와 달라질 수 있다 (예시 데이터가 매 조회마다 실시간처럼 갱신됨을 보여준다).
- 예시 데이터에 없는 지명을 입력했을 때의 동작(빈 결과, 안내 메시지 등)은 이번 acceptance criteria의 검증 대상이 아니다.
- 신분당선·공항철도 등 서울교통공사 외 사업자가 운영하는 지하철 구간이나, 환승 2회 이상인 경로는 이번 범위에서 다루지 않는다.

## Constraints and rationale

- **도착 정보는 실제 API가 아닌 예시 데이터로 채운다.** 실제 버스·지하철 도착정보 API(TAGO, 서울시 버스도착정보, 서울시 지하철 실시간 도착정보)는 공공데이터포털 개인 인증키가 있어야 호출할 수 있는데, 아직 발급받은 키가 없다. 인증키 없이는 이번 세션에서 라이브 데이터로 검증할 수 없으므로, 문서상 확인된 응답 스키마를 그대로 본뜬 예시 데이터로 입력→추천→확인 흐름 자체가 실제로 동작하는지 먼저 검증한다.
- **지하철은 서울교통공사 운영 구간만 다룬다.** 서울시 지하철 실시간 도착정보 API는 "서울시 전체역"이라고만 되어 있어, 신분당선·공항철도·수인분당선처럼 서울교통공사 외 사업자가 운영하는 수도권 노선까지 하나의 공식 API로 커버되는지 문서상 확증하지 못했다. 사용자 확인에 따라 서울교통공사 외 사업자 구간은 이번 범위와 이후 라이브 연동 모두에서 참고하지 않기로 좁혔다.
- **환승은 1회로 제한한다.** PRODUCT.md는 환승 2회 이상도 지원하도록 정의하지만, 첫 결과물은 입력→경로 안내→환승지 도착 정보 확인이라는 핵심 흐름이 실제로 동작하는지 가장 좁게 검증하는 데 집중한다. 환승 2회 이상 지원은 이 흐름이 검증된 뒤 확장한다.
- **지명 → 가까운 정류장 추천도 실제 지오코딩이 아닌 예시 데이터로 채운다.** 실제로 구현하려면 지명을 좌표로 바꾸는 지오코딩(예: 카카오 로컬 API)과, 그 좌표 주변의 정류장을 찾는 근접 정류소 조회(TAGO의 좌표기반근접정류소 목록조회 API)가 필요하다는 걸 확인했다. 두 기능 모두 실제로 존재하고 API 문서로 확인되지만, 각각 별도의 인증키가 필요하다. 이미 도착정보 API 인증키도 없는 상태에서 두 개의 키를 추가로 요구하면 이번 첫 결과물의 범위를 벗어나므로, 도착 정보와 같은 방식으로 미리 정해둔 지명-정류장 조합을 예시 데이터로 제공한다.

## Assumptions

- 실제 버스 도착정보 API의 응답 형태는 TAGO/서울시 버스도착정보 공개 문서에 나온 필드(도착예상시간[초], 남은 정류장 수, 차량유형 등)를 따른다고 가정한다.
- 실제 지하철 도착정보 API의 정확한 응답 필드는 공개 문서에서 도착예정시간·노선·역명·열차번호 정도만 확인했고, 전체 스키마는 확증하지 못했다. 예시 데이터는 이 범위 내에서 구성하고, 실제 인증키로 호출했을 때 다른 부분이 있다면 이후 조정한다.
- 지명-정류장 예시 데이터 조합(판교역/여의도/잠실역/합정 등)은 실제 위치 관계를 검증한 것이 아니라, 흐름을 보여주기 위한 예시로 구성한 것이다.

## Off-limits for this work

- 신분당선·공항철도·수인분당선 등 서울교통공사 외 사업자가 운영하는 지하철 구간 — 사용자 지시로 참고하지 않기로 범위를 좁혔다.
- 환승 2회 이상인 경로 — 핵심 흐름이 검증된 뒤 확장할 범위다.
- 실제 라이브 API 연동(버스·지하철 도착정보, 카카오 지오코딩, TAGO 좌표기반근접정류소), 인증키 발급 및 관리 — 모두 사용자의 개인 계정으로 발급받아야 하는 부분이라 이번 작업 범위 밖이다.
- 예시 데이터에 없는 임의 지명 입력에 대한 처리(검색, 오류 안내 등) — 실제 지오코딩이 없는 상태에서는 의미 있게 다룰 수 없다.
- 계정, 즐겨찾기, 경로 저장 — PRODUCT.md에서 이미 두지 않기로 확정했다.
- 위치 자동 추적(GPS 기반 자동 알림) — PRODUCT.md에서 이미 사용자가 직접 확인하는 방식으로 확정했다.

## Deferred

- 서울교통공사 외 사업자(신분당선, 공항철도, 코레일 등) 구간까지 포함하는 지하철 커버리지 확장.
- 환승 2회 이상 경로 지원.
- 실제 인증키 발급 후 라이브 API(버스·지하철 도착정보)로 전환.
- 카카오 지오코딩 API + TAGO 좌표기반근접정류소 API를 활용한 실제 지명 검색·근접 정류장 추천으로 전환.

## Remaining risks

- 서울시 지하철 실시간 도착정보 API가 실제로는 서울교통공사 구간에 한정되지 않거나(예: 9호선 일부 구간은 별도 운영사), 반대로 문서에 없는 예외가 있을 수 있어 실제 인증키로 호출해 확인이 필요하다.
- 실제 인증키로 호출했을 때 문서와 다른 응답 형태나 예외 상황(정류소/역 ID 오류, 서비스 장애 등)이 나타날 수 있으며, 예시 데이터 기반으로 만든 화면 구조가 이를 그대로 수용하지 못할 수 있다.
- 개발계정 트래픽 제한(TAGO 기준 일 10,000회)이 실제 서비스 운영 단계에서는 충분하지 않을 수 있다.
- 실제 카카오 지오코딩 + TAGO 근접 정류소 조회로 전환하면, 지명이 모호하거나(동명 지명 여러 개) 근접 정류장이 여러 개 나오는 경우를 다뤄야 하는데, 이번 예시 데이터는 지명 하나당 정류장 하나로 단순화되어 있어 그 복잡도를 반영하지 못한다.
