# 환승 도착 정보 미리보기

## User-visible outcome

사용자가 출발지·목적지 지명을 입력하면 각각에 가장 가까운 정류장/역이 추천되고, 그 두 지점을 잇는 환승 1회 경로를 안내받아, 출발역 아래에는 출발 시각을, 환승역 아래에는 도착 예정 시각과 환승할 열차의 출발 예정 시각을 구분해서(현재 시각 기준 추정치) 확인하고, 환승 지점(버스 정류장 또는 지하철역)에서 탈 다음 버스/지하철의 도착 예정 시간을 확인할 수 있다.

## Scope

- 출발지·목적지 지명 입력 → 각 지명에 가장 가까운 정류장/역 추천 → 그 두 지점을 잇는, 환승 지점 1곳을 포함한 경로(첫 구간, 환승 지점, 다음 구간) 안내
- 지명과 가까운 정류장/역의 매칭, 그리고 도착 정보는 모두 예시 데이터로 제공한다. 실제 지오코딩을 수행하지 않는다
- 4호선(진접선·서울 지하철 4호선·과천선·안산선 포함 전체 53개 역)과 9호선(전체 38개 역)은 실제 노선도상 순서를 기반으로 어떤 두 역을 골라도 경로가 만들어진다. 두 노선의 유일한 환승역인 동작역을 기준으로, 서로 다른 노선의 역끼리는 동작역에서 환승하는 경로를 구성한다. 같은 노선 안의 두 역을 고르면 애초에 환승이 필요 없는 구간이므로, 경로 대신 "환승이 필요 없다"는 안내를 보여준다
- 위 두 노선 외의 지명(판교역·여의도·잠실역·합정 등 기존 예시)은 여전히 손으로 정해둔 소수의 예시 조합으로만 경로가 나온다. 실제 경로 탐색 엔진을 만들지 않는다
- 경로찾기 버튼을 누르는 순간(현재 시각)을 출발역 시각으로 삼아, 첫 구간의 예상 소요 시간만큼 더한 시각을 환승역 도착 예정 시각으로 계산해 출발역·환승역 각각의 이름 아래에 보여준다. 실제 열차 시각표를 조회하지 않고, 4호선·9호선처럼 노선 순서를 아는 구간은 역 개수 기반으로, 그 외 손으로 정한 예시 조합은 미리 정해둔 소요 시간으로 추정한다
- 환승역 아래에는 도착 예정 시각과 별개로, 환승할 열차(다음 구간)가 그 역에서 출발하는 예정 시각도 구분해서 보여준다. 도착 예정 시각에 정해둔 환승 대기 시간을 더해 계산한다
- 환승 지점에서 사용자가 확인하면, 그 지점에서 탈 다음 교통편(버스 또는 지하철)의 도착 예정 시간을 볼 수 있다
- 이동 수단은 버스와 지하철을 다룬다. 지하철은 운영 사업자를 가리지 않고 다룬다(서울교통공사, 코레일 운영 구간인 과천선 등, 서울시메트로9호선이 운영하는 9호선 등을 모두 예시 데이터에 포함할 수 있다). 예시 데이터로만 동작하는 이번 범위에서는 운영사가 실제 API 연동에 영향을 주지 않기 때문이다
- 도착 정보는 실제 버스 도착정보 API(TAGO/서울시 버스도착정보)와 서울시 지하철 실시간 도착정보 API의 응답 스키마를 그대로 본뜬 예시 데이터로 제공한다. 새로 조회할 때마다 예시 데이터 내에서 값이 달라져, 정적으로 고정된 화면이 아니라 매 조회마다 갱신되는 동작을 확인할 수 있다
- 환승은 1회(구간 2개)로 제한한다
- 위치를 자동으로 추적하지 않는다. 사용자가 직접 확인 동작을 해야 도착 정보가 갱신된다 (PRODUCT.md 확정 사항)
- 경로나 이전 조회를 저장하는 계정·즐겨찾기 기능은 두지 않는다 (PRODUCT.md 확정 사항)

## Acceptance criteria

- 미리 정해둔 예시 지명 중 하나를 출발지에, 다른 하나를 목적지에 입력하면, 각각에 가장 가까운 정류장/역이 추천된다.
  - 예시 1: 출발지 "판교역"을 입력하면 "판교역.버스환승센터" 정류장이, 목적지 "잠실역"을 입력하면 "잠실역"이 추천된다.
  - 예시 2: 출발지 "여의도"를 입력하면 "여의도역" 정류장이, 목적지 "합정"을 입력하면 "합정역"이 추천된다.
- 추천된 두 지점을 잇는, 환승 지점 1곳을 포함한 경로(첫 구간 → 환승 지점 → 다음 구간)가 화면에 표시된다. 구간은 버스 또는 지하철 구간일 수 있다 (예시 1의 경우 "판교역.버스환승센터"에서 버스 탑승 → "강남역"에서 하차해 지하철로 환승 → 2호선으로 잠실 방향 이동, 과 같은 흐름).
- 4호선의 역과 9호선의 역을 각각 출발지·목적지로 입력하면, 동작역에서 환승하는 경로가 화면에 표시된다. 어떤 4호선 역-9호선 역 조합을 넣어도 동일하게 동작한다 (예시: 출발지 "평촌역"을 입력하면 그 역 자체가 추천되고, 목적지 "마곡나루역"을 입력하면 역시 그 역 자체가 추천되며, "평촌역"에서 4호선을 타고 "동작역"에서 9호선으로 환승해 "마곡나루역"까지 가는 경로가 표시된다).
- 같은 노선(4호선 안, 또는 9호선 안)의 두 역을 입력하면, 경로 대신 "환승이 필요 없는 구간"이라는 안내가 표시된다.
- 경로가 표시될 때 출발역 이름 아래에 출발 시각(현재 시각)이 표시된다.
- 환승역 이름 아래에 도착 예정 시각과, 환승할 열차의 출발 예정 시각이 구분되어 표시된다 (두 값은 서로 다르다).
- 환승 지점에서 다음에 탈 교통편(버스 또는 지하철)의 도착 예정 시간이 화면에 표시된다.
- 같은 환승 지점을 다시 조회하면 도착 예정 시간 값이 이전 조회와 달라질 수 있다 (예시 데이터가 매 조회마다 실시간처럼 갱신됨을 보여준다).
- 예시 데이터에 없는 지명을 입력했을 때의 동작(빈 결과, 안내 메시지 등)은 이번 acceptance criteria의 검증 대상이 아니다.
- 환승 2회 이상인 경로는 이번 범위에서 다루지 않는다.

## Constraints and rationale

- **도착 정보는 실제 API가 아닌 예시 데이터로 채운다.** 실제 버스·지하철 도착정보 API(TAGO, 서울시 버스도착정보, 서울시 지하철 실시간 도착정보)는 공공데이터포털 개인 인증키가 있어야 호출할 수 있는데, 아직 발급받은 키가 없다. 인증키 없이는 이번 세션에서 라이브 데이터로 검증할 수 없으므로, 문서상 확인된 응답 스키마를 그대로 본뜬 예시 데이터로 입력→추천→확인 흐름 자체가 실제로 동작하는지 먼저 검증한다.
- **지하철은 운영 사업자를 가리지 않고 다룬다.** 처음에는 서울시 지하철 실시간 도착정보 API의 커버리지가 불확실해 서울교통공사 운영 구간만 다루기로 좁혔었다. 그런데 사용자가 요청한 평촌역(4호선 과천선 구간, 코레일 운영)과 마곡나루역(9호선, 서울시메트로9호선 운영 / 공항철도)이 실제로는 서울교통공사가 아닌 사업자 구간으로 확인되면서, 이번 범위를 다시 사용자와 함께 검토했다. 이번 결과물은 실제 API를 호출하지 않고 예시 데이터로만 동작하므로, 운영사 구분이 지금 당장의 구현 가능 여부에 영향을 주지 않는다는 점을 확인하고 운영사 제한을 없애기로 했다. 다만 실제 라이브 API로 전환할 때는 운영사별로 API를 따로 연동해야 할 수 있다는 점은 여전히 남는 리스크다.
- **환승은 1회로 제한한다.** PRODUCT.md는 환승 2회 이상도 지원하도록 정의하지만, 첫 결과물은 입력→경로 안내→환승지 도착 정보 확인이라는 핵심 흐름이 실제로 동작하는지 가장 좁게 검증하는 데 집중한다. 환승 2회 이상 지원은 이 흐름이 검증된 뒤 확장한다.
- **4호선·9호선은 노선 목록 기반으로 경로를 생성하고, 그 외 지명은 손으로 정한 예시 조합만 지원한다.** 위키백과에서 확인한 두 노선의 실제 역 순서와, 두 노선의 유일한 환승역이 동작역이라는 사실을 근거로 삼았다. 서로 다른 노선의 역끼리는 항상 동작역 환승으로 경로가 생성되고, 같은 노선끼리는 환승이 필요 없으므로 별도 안내로 처리한다. 그 외 지명(판교역 등)까지 이 방식으로 일반화하려면 모든 버스 노선의 실제 지리 데이터가 필요해 이번 범위를 넘어서므로, 손으로 정한 예시 조합 방식을 그대로 둔다.
- **출발역·환승역 시각은 실제 열차 시각표가 아닌 추정치로 계산한다.** 서울교통공사 열차운행시각표는 인증키 없이 파일로 받을 수 있다는 걸 확인했지만, 서울교통공사가 직접 관할하는 구간만 있고 4호선의 과천선·안산선·진접선(코레일)이나 9호선(서울시메트로9호선) 구간은 빠져 있어, 지금 다루는 90개 역 상당수를 커버하지 못한다. 실제 파일을 내려받아 역 코드까지 매칭해 파싱하는 건 이번 스펙의 다른 부분과 비교해 훨씬 큰 작업이라, 사용자와 상의해 추정치 방식으로 정했다.
- **지명 → 가까운 정류장 추천도 실제 지오코딩이 아닌 예시 데이터로 채운다.** 실제로 구현하려면 지명을 좌표로 바꾸는 지오코딩(예: 카카오 로컬 API)과, 그 좌표 주변의 정류장을 찾는 근접 정류소 조회(TAGO의 좌표기반근접정류소 목록조회 API)가 필요하다는 걸 확인했다. 두 기능 모두 실제로 존재하고 API 문서로 확인되지만, 각각 별도의 인증키가 필요하다. 이미 도착정보 API 인증키도 없는 상태에서 두 개의 키를 추가로 요구하면 이번 첫 결과물의 범위를 벗어나므로, 도착 정보와 같은 방식으로 미리 정해둔 지명-정류장 조합을 예시 데이터로 제공한다.

## Assumptions

- 실제 버스 도착정보 API의 응답 형태는 TAGO/서울시 버스도착정보 공개 문서에 나온 필드(도착예상시간[초], 남은 정류장 수, 차량유형 등)를 따른다고 가정한다.
- 실제 지하철 도착정보 API의 정확한 응답 필드는 공개 문서에서 도착예정시간·노선·역명·열차번호 정도만 확인했고, 전체 스키마는 확증하지 못했다. 예시 데이터는 이 범위 내에서 구성하고, 실제 인증키로 호출했을 때 다른 부분이 있다면 이후 조정한다.
- 지명-정류장 예시 데이터 조합(판교역/여의도/잠실역/합정/평촌역/마곡나루역 등)은 실제 위치 관계를 검증한 것이 아니라, 흐름을 보여주기 위한 예시로 구성한 것이다.
- 4호선·9호선의 역 이름과 순서는 위키백과 기준으로 확인했지만, 각 구간의 실제 소요 시간이나 배차 간격을 반영한 것은 아니다. 도착 예정 시간은 여전히 무작위 예시 값이다.
- 4호선과 9호선을 동시에 지나는 역(동작역)을 출발지나 목적지로 입력하면, 이미 환승 지점 자체이므로 "환승이 필요 없는 구간"으로 안내한다.
- 4호선·9호선처럼 노선 순서를 아는 구간은 역 1개당 2분이 걸린다고 가정해 소요 시간을 추정한다. 그 외 손으로 정한 예시 조합(판교역·여의도 등 버스 구간)은 노선 순서 데이터가 없어, 역 간격 대신 미리 정해둔 대략적인 소요 시간 값을 사용한다. 둘 다 실제 배차·소요시간을 측정한 값이 아니다.
- 환승 대기 시간(환승역 도착부터 다음 열차 출발까지)은 실제 배차 간격을 계산한 값이 아니라, 모든 경로에 동일하게 적용하는 고정 추정치(5분)를 사용한다.

## Off-limits for this work

- 환승 2회 이상인 경로 — 핵심 흐름이 검증된 뒤 확장할 범위다.
- 실제 라이브 API 연동(버스·지하철 도착정보, 카카오 지오코딩, TAGO 좌표기반근접정류소), 인증키 발급 및 관리 — 모두 사용자의 개인 계정으로 발급받아야 하는 부분이라 이번 작업 범위 밖이다.
- 예시 데이터에 없는 임의 지명 입력에 대한 처리(검색, 오류 안내 등) — 실제 지오코딩이 없는 상태에서는 의미 있게 다룰 수 없다.
- 계정, 즐겨찾기, 경로 저장 — PRODUCT.md에서 이미 두지 않기로 확정했다.
- 위치 자동 추적(GPS 기반 자동 알림) — PRODUCT.md에서 이미 사용자가 직접 확인하는 방식으로 확정했다.

## Deferred

- 4호선·9호선 외 다른 노선까지 노선 목록 기반 경로 생성 방식 확장.
- 환승 2회 이상 경로 지원.
- 실제 인증키 발급 후 라이브 API(버스·지하철 도착정보)로 전환.
- 카카오 지오코딩 API + TAGO 좌표기반근접정류소 API를 활용한 실제 지명 검색·근접 정류장 추천으로 전환.
- 지하철 운영사별(서울교통공사, 코레일, 서울시메트로9호선, 공항철도, 신분당선 등) 실제 라이브 API 연동 — 예시 데이터 단계에서는 운영사를 가리지 않지만, 실제 API로 전환하면 운영사마다 API가 다를 수 있어 별도 조사·연동이 필요하다.
- 서울교통공사가 인증키 없이 제공하는 열차운행시각표 파일을 실제로 내려받아 파싱하는 방식으로 전환 (다만 서울교통공사 관할 구간에 한해서만 커버 가능하다는 한계는 남는다).

## Remaining risks

- 지하철 운영사가 서울교통공사, 코레일(과천선 등), 서울시메트로9호선, 공항철도 등으로 나뉘어 있다는 게 이번에 확인됐다. 실제 라이브 연동 단계에서 이 운영사들이 각각 다른 API·인증키를 요구할 수 있고, 일부는 공식 공공 API가 아예 없을 수도 있다.
- 실제 인증키로 호출했을 때 문서와 다른 응답 형태나 예외 상황(정류소/역 ID 오류, 서비스 장애 등)이 나타날 수 있으며, 예시 데이터 기반으로 만든 화면 구조가 이를 그대로 수용하지 못할 수 있다.
- 개발계정 트래픽 제한(TAGO 기준 일 10,000회)이 실제 서비스 운영 단계에서는 충분하지 않을 수 있다.
- 실제 카카오 지오코딩 + TAGO 근접 정류소 조회로 전환하면, 지명이 모호하거나(동명 지명 여러 개) 근접 정류장이 여러 개 나오는 경우를 다뤄야 하는데, 이번 예시 데이터는 지명 하나당 정류장 하나로 단순화되어 있어 그 복잡도를 반영하지 못한다.
